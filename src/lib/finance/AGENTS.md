- Web push is sent server-side by `src/lib/finance/web-push.server.ts` (pure Web Crypto VAPID + aes128gcm) — a DB trigger on new `marcia_notification` rows calls `/api/public/push/dispatch` via pg_net with a token kept in deny-all `push_dispatch_secret`; the browser gets the public key from `getPushPublicKey` — why: the `web-push` npm lib breaks on the Worker runtime and the private key never reaches the browser.
- Notice generation (due bills, budget, plan expiry, credits, daily summary, payment confirmed) lives in `src/lib/finance/notification-jobs.server.ts` with pure rules in `notification-rules.ts`; it runs both on app open and from the scheduled `/api/public/cron/reminders` route, and push dispatch applies per-user `notification_preference` (categories, quiet hours) — why: one idempotent path.
- Notices also go out on WhatsApp from the same push dispatch route (`notification-whatsapp.server.ts`, gated by `shouldSendWhatsapp`, to the user's `fin_whatsapp_identity` phone through the active central channel); monthly PDF reports are built with `pdf-lib` in `monthly-report.server.ts` (pure totals in `monthly-report-rules.ts`) — why: one delivery path per notice, and pdf-lib runs on the Worker runtime.
- The MIA profile ("Personalidade e regras") lives in `company.finance_profile`, normalized by `src/lib/ai/assistant-profile-rules.ts` and saved only via `saveAssistantProfile`; app chat, WhatsApp and notice jobs read it through the same rules — why: every channel behaves the same.
- Subscriber settings (`/app/configuracoes?aba=`) save MIA preferences only via `saveAssistantProfile` and read plan/channel status via `src/lib/finance/settings.functions.ts`; account deletion is a request in `account_deletion_request` resolved by the owner in Master — why: no settings screen can overwrite the shared MIA profile, and data removal stays a human decision.
- Planner actions (pay/move/edit/delete/undo, new bills, recurrences, extras, period PDFs) live in `src/lib/finance/finance-planner.functions.ts`; editing a single recurrence occurrence materializes a `fin_lancamento` with `recorrencia_id` and `metadata.recurrence_date` (cancelled rows hide deleted occurrences), and every action re-runs `runAllForUser` — why: calendar, statement and notices stay consistent.
- Statement (Movimentações) actions live in `src/lib/finance/finance-transactions.functions.ts` (pay/unpay/edit/delete/duplicate, bulk, undo, budgets) with pure rules in `src/lib/finance/transactions-rules.ts`; deletes set status `cancelado`, category edits can teach MIA via `finance_profile.category_rules`, and every action re-runs `runAllForUser` — why: same path as the planner; undo works.
- Statement splits live in `fin_lancamento_split` (sum must equal the entry, validated in `setTransactionSplits`) and tags in `fin_lancamento.tags`; category totals (charts, budgets, PDF) count split parts instead of the entry category; bank imports (OFX/CSV parsed client-side by `bank-statement-rules.ts`) write `fonte: importacao` with `metadata.import_batch` for batch undo — why: one rule for every category total and safe re-imports.
- Month overview comparisons/alerts/tips come from pure rules in `src/lib/finance/overview-rules.ts`; bill actions reuse `plannerItemAction` — why: no new server path, demo mirrors it.
