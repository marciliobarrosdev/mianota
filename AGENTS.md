- Global integration credentials (Evolution, Google OAuth, Stripe) live encrypted (AES-256-GCM, server-derived key) in deny-all `platform_integration_secret`; read them only via `resolveIntegration` in `src/lib/common/integration-secrets.server.ts` (env is fallback) — why: owners configure in Master without Secrets and values never reach the browser.
- Installation ownership is auto-claimed inside `bootstrap_remix_instance` by the first confirmed Auth account, once, under an advisory lock — why: no manual activation code, still race-safe.
- Two independent auth sessions per browser: subscriber (generated client, default storage key) for `/entrar` and `/app/*`; owner via `superadminSupabase` (`src/lib/auth/superadmin-client.ts`, own storageKey) for `/superadmin` and `/master/*`. Shared code imports `supabase` from `src/lib/auth/realm-supabase.ts`, which resolves the tab's realm (admin paths, or `/app` during a Master impersonation in that tab); server-fn bearer comes from `attachRealmSupabaseAuth` in `src/start.ts`; sign-outs use `signOutRealm` (scope local) — why: owner and subscriber stay logged in side by side without overwriting each other. Enforced by `scripts/verify-auth-realms.mjs`.
- Subscriber finance screens (month overview, statement, planner/calendar, MárcIA chat) are shared presentational components in `src/components/finance/*` fed by `/app` (real server functions) and `/demo` (fictitious data in `src/lib/finance/finance-demo-data.ts`, scripted chat with the same `MiaChatController` contract); period/status rules live in `src/lib/finance/finance-period.ts` — why: demo mirrors the product, no duplicate UI.
- Removed areas stay as redirect-only route files — why: old links keep working.
- The central WhatsApp channel is exclusive: `platform_support_channel.active_provider` changes only through the `switch_central_channel` RPC (trigger-guarded; it only activates when the shared channel row describes that provider as connected, Meta also needs `test_ok`), and sends require `isActiveChannelConnected`; webhooks drop inbound messages from the inactive provider — why: QR Code and Meta can never answer at the same time.
- Post-purchase WhatsApp onboarding lives in `src/lib/whatsapp/purchase-onboarding.server.ts` (pure rules in `purchase-onboarding-rules.ts`): idempotent per billing event, runs after subscription/credits, never throws into payment webhooks, stores only hashes of one-time activation codes/tokens, and binds a phone to a tenant only on the first valid reply from the exact buyer phone (codes/tokens from other numbers are rejected without being consumed) — why: no silent binding or duplicate sends.
- AI provider selection (Lovable AI default, optional single BYOK OpenAI/Anthropic/OpenRouter/Gemini) is read from `ai_provider_config` inside `lovableAiChat`; OpenRouter/Gemini model ids come from the `ai_model_catalog` table (with media capabilities; unsupported attachments are converted to text first), and BYOK keys are stored via `integration-secrets.server.ts` and only shown masked — why: one entry point for every AI call, no hardcoded models, keys never reach the browser.
- New subscriptions always start from an explicit active plan: generic signup CTAs go to `/#planos`, `/entrar?modo=signup` without a valid active `plano` redirects there, and both `createCheckoutCompany` (`src/lib/billing/plan-selection.ts`) and the `create_checkout_company_atomic` RPC reject a missing/inactive slug — why: no company or subscription is ever created on an assumed default plan.
- Human form values go through shared helpers: money via `src/lib/common/money.ts` + `MoneyInput` (UI shows "R$ 0,00", storage/Stripe keep integer cents), phones via `src/lib/common/phone.ts` (BR mask, E.164 on the server), e-mails via `normalizeEmail`/`emailError` in `src/lib/common/masks.ts`; technical IDs/tokens are never masked — why: one conversion path prevents 100x price errors and inconsistent contact data.
- InfinitePay: each plan's checkout link and price live on the plan row (edited in /master/planos; env Link 1/Link 2 are fallback via `checkoutLinkForPlan`); the unsigned webhook re-confirms via `payment_check`, maps plan by paid amount against current active plan prices (prices must be unique) and company by buyer e-mail, then calls shared `applyEvent` — why: owner edits apply everywhere; forged notices grant nothing.
- Free-plan once-per-account is enforced server-side via `free_plan_usage` (keyed by normalized owner e-mail, also matched by auth user id), checked before creating the owner and recorded after the subscriber is created — why: plan rows can change later, so usage history must live on its own.
- src/lib is grouped by domain folders (finance, ai, whatsapp, master, billing, common, auth); only utils.ts stays at root — why: shadcn imports @/lib/utils.
- Subscriber photos use 256px data URLs — why: public buckets are blocked.
- Identity rules map lowercase form types to uppercase storage — why: preserve the company constraint.
- Sensitive Master actions (admins, integration keys, suspensions, billing reprocess) are logged via `writeMasterAudit` (`src/lib/master/master-audit.server.ts`) into super-admin-read-only `master_audit_log`; it never throws — why: one security trail that cannot break the action.
- Subdirectories (e.g. src/lib/finance) have their own AGENTS.md; read it before changing files there.
- Plan acquisition/upgrade/downgrade and the "needs payment" gate live in `src/lib/billing/plan-transition-rules.ts`; public signup stores the full subscriber form in auth metadata `signup_profile`, applied to the company by `createCheckoutCompany` — why: one rule set for landing, checkout and /app guard.
- Master CRM leads (`master_lead*`, super-admin RLS) are fed by `src/lib/master/lead-sync.server.ts` from free signup (`createCheckoutCompany`) and payment `applyEvent`; hooks never throw — why: CRM must not break signup or payments.
