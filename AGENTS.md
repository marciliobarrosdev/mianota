- Global integration credentials (Evolution, Google OAuth, Stripe) live encrypted (AES-256-GCM, server-derived key) in deny-all `platform_integration_secret`; read them only via `resolveIntegration` in `src/lib/integration-secrets.server.ts` (env is fallback) — why: owners configure in Master without Secrets and values never reach the browser.
- Installation ownership is auto-claimed inside `bootstrap_remix_instance` by the first confirmed Auth account, once, under an advisory lock — why: no manual activation code, still race-safe.
- Two independent auth sessions per browser: subscriber (generated client, default storage key) for `/entrar` and `/app/*`; owner via `superadminSupabase` (`src/lib/auth/superadmin-client.ts`, own storageKey) for `/superadmin` and `/master/*`. Shared code imports `supabase` from `src/lib/auth/realm-supabase.ts`, which resolves the tab's realm (admin paths, or `/app` during a Master impersonation in that tab); server-fn bearer comes from `attachRealmSupabaseAuth` in `src/start.ts`; sign-outs use `signOutRealm` (scope local) — why: owner and subscriber stay logged in side by side without overwriting each other. Enforced by `scripts/verify-auth-realms.mjs`.
- Subscriber finance screens (month overview, statement, planner/calendar, MárcIA chat) are shared presentational components in `src/components/finance/*` fed by `/app` (real server functions) and `/demo` (fictitious data in `src/lib/finance-demo-data.ts`, scripted chat with the same `MarciaChatController` contract); period/status rules live in `src/lib/finance-period.ts` — why: the demo always mirrors the real product without duplicate UI.
- Removed areas stay as redirect-only route files to their new equivalent (e.g. `/app/calendario` → `/app/planejamento`) — why: old links, reminders and bookmarks keep working.
- The central WhatsApp channel is exclusive: `platform_support_channel.active_provider` changes only through the `switch_central_channel` RPC (trigger-guarded; it only activates when the shared channel row describes that provider as connected, Meta also needs `test_ok`), and sends require `isActiveChannelConnected`; webhooks drop inbound messages from the inactive provider — why: QR Code and Meta can never answer at the same time.
- Post-purchase WhatsApp onboarding lives in `src/lib/purchase-onboarding.server.ts` (pure rules in `purchase-onboarding-rules.ts`): idempotent per billing event, runs after subscription/credits, never throws into payment webhooks, stores only hashes of one-time activation codes/tokens, and binds a phone to a tenant only on the first valid reply from the exact buyer phone (codes/tokens from other numbers are rejected without being consumed) — why: no silent phone binding and no duplicate sends. Enforced by `tests/purchase-onboarding.test.ts` and `scripts/verify-central-channel-onboarding.mjs`.
- AI provider selection (Lovable AI default, optional single BYOK OpenAI/Anthropic) is read from `ai_provider_config` inside `lovableAiChat`; BYOK keys are stored via `integration-secrets.server.ts` and only shown masked — why: one entry point for every AI call and keys never reach the browser.
- New subscriptions always start from an explicit active plan: generic signup CTAs go to `/#planos`, `/entrar?modo=signup` without a valid active `plano` redirects there, and both `createCheckoutCompany` (`src/lib/plan-selection.ts`) and the `create_checkout_company_atomic` RPC reject a missing/inactive slug — why: no company or subscription is ever created on an assumed default plan.
- Human form values go through shared helpers: money via `src/lib/money.ts` + `MoneyInput` (UI shows "R$ 0,00", storage/Stripe keep integer cents), phones via `src/lib/phone.ts` (BR mask, E.164 on the server), e-mails via `normalizeEmail`/`emailError` in `src/lib/masks.ts`; technical IDs/tokens are never masked — why: one conversion path prevents 100x price errors and inconsistent contact data.
- InfinitePay: each plan's checkout link and price live on the plan row (edited in /master/planos; env Link 1/Link 2 are fallback via `checkoutLinkForPlan`); the unsigned webhook re-confirms via `payment_check`, maps plan by paid amount against current active plan prices (prices must be unique) and company by buyer e-mail, then calls shared `applyEvent` — why: owner edits take effect everywhere and forged notices grant nothing.
- Free-plan once-per-account is enforced server-side via `free_plan_usage` (keyed by normalized owner e-mail, also matched by auth user id), checked before creating the owner and recorded after the subscriber is created — why: plan rows can change later, so usage history must live on its own.
- Web push is sent server-side by `src/lib/web-push.server.ts` (pure Web Crypto VAPID + aes128gcm) — a DB trigger on new `marcia_notification` rows calls `/api/public/push/dispatch` via pg_net with a token kept in deny-all `push_dispatch_secret`; the browser gets the public key from `getPushPublicKey` — why: the `web-push` npm lib breaks on the Worker runtime and the private key never reaches the browser.
- Notice generation (due bills, budget, plan expiry, credits, daily summary, payment confirmed) lives in `src/lib/notification-jobs.server.ts` with pure rules in `notification-rules.ts`; it runs both on app open and from the scheduled `/api/public/cron/reminders` route, and push dispatch applies per-user `notification_preference` (categories, quiet hours) — why: one idempotent path whether or not the user opens the app.
- Notices also go out on WhatsApp from the same push dispatch route (`notification-whatsapp.server.ts`, gated by `shouldSendWhatsapp`, to the user's `fin_whatsapp_identity` phone through the active central channel); monthly PDF reports are built with `pdf-lib` in `monthly-report.server.ts` (pure totals in `monthly-report-rules.ts`) — why: one delivery path per notice, and pdf-lib runs on the Worker runtime.
- The MIA profile ("Personalidade e regras") lives in `company.finance_profile`, normalized by `src/lib/assistant-profile-rules.ts` and saved only via `saveAssistantProfile`; app chat, WhatsApp and notice jobs read it through the same rules — why: one validated source so every channel behaves the same.
- Subscriber settings (`/app/configuracoes?aba=`) save MIA preferences only via `saveAssistantProfile` and read plan/channel status via `src/lib/settings.functions.ts`; account deletion is a request in `account_deletion_request` resolved by the owner in Master — why: no settings screen can overwrite the shared MIA profile, and data removal stays a human decision.
- Planner actions (pay/move/edit/delete/undo, new bills, recurrences, extras, period PDFs) live in `src/lib/finance-planner.functions.ts`; editing a single recurrence occurrence materializes a `fin_lancamento` with `recorrencia_id` and `metadata.recurrence_date` (cancelled rows hide deleted occurrences), and every action re-runs `runAllForUser` — why: the calendar, Movimentações and notices stay consistent without schema changes.
- Statement (Movimentações) actions live in `src/lib/finance-transactions.functions.ts` (pay/unpay/edit/delete/duplicate, bulk, undo, budgets) with pure rules in `src/lib/transactions-rules.ts`; deletes set status `cancelado`, category edits can teach MIA via `finance_profile.category_rules`, and every action re-runs `runAllForUser` — why: same consistency path as the planner, undo stays possible.
- Statement splits live in `fin_lancamento_split` (sum must equal the entry, validated in `setTransactionSplits`) and tags in `fin_lancamento.tags`; category totals (charts, budgets, PDF) count split parts instead of the entry category; bank imports (OFX/CSV parsed client-side by `bank-statement-rules.ts`) write `fonte: importacao` with `metadata.import_batch` for batch undo — why: one rule for every category total and safe re-imports.
- Month overview comparisons/alerts/tips come from pure rules in `src/lib/overview-rules.ts`; bill actions reuse `plannerItemAction` — why: no new server path, demo mirrors it.
